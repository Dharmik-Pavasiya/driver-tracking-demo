# Driver Location

A small **Android/iOS-only** Flutter assessment app using **GetX**. The screen has Start/Stop, the latest coordinates, pending/synced counts, two testing controls and recent records. Tracking uses native location services in both foreground and background. A phone supplies real GPS; an emulator/simulator can supply simulated GPS through the same code.

## Run

Tools used: Flutter 3.47.0, Dart 3.13.0. Android needs its SDK and Java 17 or a compatible newer JDK. iOS needs macOS, Xcode and the normal Flutter iOS toolchain. The project has no web or desktop target.

```sh
git clone https://github.com/Dharmik-Pavasiya/driver-tracking-demo.git
cd driver-tracking-demo
flutter pub get
```

Start the mock server from the project root in one terminal:

```sh
dart run mock_api/server.dart
```

Run the app in another terminal:

```sh
flutter devices
flutter run -d <device-id>
```

The default API URL is `http://10.0.2.2:8081` for an Android emulator and `http://localhost:8081` for an iOS simulator on the same Mac. For an Android USB device:

```sh
adb reverse tcp:8081 tcp:8081
flutter run -d <device-id> --dart-define=API_BASE_URL=http://127.0.0.1:8081
```

For a physical iPhone, use an API reachable from that phone. The local mock can bind to your development computer's LAN interface with `dart run mock_api/server.dart 8081 0.0.0.0`; pass its LAN URL with `--dart-define=API_BASE_URL=http://<computer-lan-ip>:8081`. Permit local networking on iOS. For development LAN IP HTTP testing, configure a suitable debug-only ATS exception or use HTTPS. The committed ATS setting permits local hostnames; release deployment should use HTTPS. The mock has no authentication and is intended only for local testing.

Press **Start tracking**, grant location permission and allow the Android notification. Start from the visible screen before minimizing/locking. A GPS fix may take a few seconds. Locations are requested at high accuracy with a ten-metre distance filter; moving the phone or injecting another emulator coordinate creates another record. Stationary points are not generated by a Dart timer.

For simulated locations, Android Emulator → Extended Controls → Location can send a point or route. iOS Simulator → Features → Location can select a route or custom coordinate. These are native GPS simulations, so they also exercise the background implementation.

## Quick demonstration

1. Enable **Simulate offline**, then Start. Move/inject locations. Pending increases and rows remain in SQLite.
2. Minimize or lock during the active session. Continue moving/injecting locations, then reopen the app to inspect saved points.
3. Disable offline simulation. Pending rows synchronize automatically. Stop ends native GPS acquisition, while saved records remain eligible for upload.
4. Select **Fail before saving** and capture a point. HTTP 503 leaves it pending with its attempts/error. Select Healthy and wait for retry, or use Retry pending uploads.
5. Select **Fail after saving** and capture a point. The server commits it but returns 503. Retry uses the same ID and succeeds without creating another server record, even if this failure option stays selected.
6. `GET http://localhost:8081/locations` shows unique server records. Stop the server, collect points, close/reopen the app and restart the server to check persistence through restart.

Tracking and the test switches reset after app termination; saved records and retry deadlines survive. Start must be pressed again after a process restart. The UI shows the latest ten records; the database retains all of them.

## Structure

This follows [your GetX template](https://github.com/Dharmik-Pavasiya/getx-architechture): feature-first folders, route bindings, an injected repository, `GetxController`, `GetView` and `Obx`. The assessment has one screen, so it does not need splash screens, extra navigation or a large API abstraction stack.

```text
lib/
  main.dart                       Open SQLite, then start the app
  app/app_binding.dart            Register shared dependencies
  router/                         Route names and page bindings
  network/
    connectivity/                 Observe connectivity + offline override
    api_provider/                 HTTP upload and acknowledgement validation
  screens/tracking_screen/
    binding/                      Inject dependencies into the controller
    controller/                   Start/stop, reactive state and lifecycle
    data/                         Location model and SQLite repository
    service/                      Native GPS and synchronization worker
    view/                         Standard Material UI
mock_api/server.dart              Local REST mock with persisted deduplication
test/                             Repository, retry, API and GetX lifecycle tests
```

Each application class and method has a Dart documentation comment. Start reading `TrackingController.startTracking`, then `_saveLocation`, `LocationRepository.enqueue`, `SyncService.synchronize` and `RestLocationApi.upload` to follow the whole flow.

## How a location moves through the app

1. `DeviceLocationService.prepare()` checks GPS and permission while the user is on screen.
2. `start()` subscribes to native positions. Each fix gets one UUID and a UTC capture time.
3. `TrackingController._saveLocation()` **awaits the SQLite insert before any upload**.
4. `SyncService` reads the oldest pending row whose retry time is due. It counts the attempt and sends that row to the API.
5. A successful reply must contain `accepted: true` and the same ID. Only then is that row marked synced.
6. A failed request saves its error and next retry time. Connectivity return, app resume, new fixes and the retry timer trigger another pass.

GetX `Rx` fields update the view. `ever` workers react to network/sync changes. SQL stays in the repository; permissions stay in the location service; HTTP stays in the API class. Dependencies are passed to the controller constructor, which makes its tests independent of real devices.

## Reliability decisions

- SQLite is the source of truth. IDs are primary keys. Each insert/update is atomic and targets one record, so acknowledging an upload cannot overwrite a concurrently captured point.
- Only one sync pass runs at a time; repeated triggers share its future.
- Requests time out after eight seconds. Connectivity reports transport availability, not server reachability.
- Retry delays are 2, 4, 8, 16, 32 and 60 seconds, capped at 60 seconds, plus up to 500ms jitter. Attempts and deadlines are persisted. HTTP 408/429/5xx and network/protocol failures retry. Other HTTP rejections become blocked until explicit review/retry.
- Delivery is **at least once** with idempotent acceptance. If the server commits and the reply is lost, another request is expected. `Idempotency-Key` is the original UUID. Same ID/same payload is acknowledged; same ID/different payload returns 409. No exactly-once network guarantee is claimed.
- The mock serializes requests and writes accepted records to an atomically replaced JSON file before replying. It retains IDs across server restarts. Runtime mock data is ignored by Git.

## Native background implementation

The Android adapter uses `forceLocationManager: true` for the native GPS provider. It works with emulator GPS injection and devices without Google Play location services. Real GPS reception is still required on a physical phone.

**Android:** `AndroidSettings.foregroundNotificationConfig` starts Geolocator's native `GeolocatorLocationService`. Its manifest merges `foregroundServiceType="location"`; the app declares foreground-service/location/wake-lock permissions and coarse/fine location. A wake lock supports delivery while the screen is off. The ongoing notification explains tracking; Android 13+ notification permission is requested. Denial does not stop the foreground service, but Android may show it only in the active-apps/task-manager UI. Cancelling the GPS subscription stops the service and its notification. A journey is started while the activity is visible, so while-in-use location permission is sufficient for that ongoing foreground service; this demo does not auto-start from the background. Additional background location authorization and modern foreground-start restrictions matter for restart-from-background use cases.

**iOS:** `Info.plist` includes location usage descriptions and `UIBackgroundModes: location`; the Xcode target has the Background Modes capability. `AppleSettings` enables background updates, disables automatic pausing during an active journey, selects automotive navigation, and shows the system location indicator. Geolocator uses native `CLLocationManager`. This is iOS's location background execution pathway, not an Android-style foreground service or a generic Dart background daemon. Authorization is requested before starting. When-in-use permission can continue an active authorized background location session; Always authorization is relevant to additional relaunch/background-start use cases. Stop cancels native location updates.

The controller does **not** cancel tracking on paused/inactive lifecycle states. It rechecks connectivity and SQLite on resume. Every delivered native fix is stored before syncing. On iOS, native location callbacks also trigger sync; a Dart retry timer alone cannot keep a suspended app alive. If tracking is stopped while offline and iOS later suspends the app, remaining uploads resume when the app receives another permitted execution window or is reopened. An exact background upload time is not guaranteed.

Screen lock differs from process termination. Android force-stop, iOS user force-quit, revoked permissions, disabled GPS, OEM battery policies and OS termination can end tracking. The app does not promise recovery after these events or auto-restart after reboot. Production extensions would add OS-scheduled upload work (WorkManager/background URLSession), retention limits and real-device battery tests. For iOS locked-device storage, validate database file protection after first unlock on the target devices; do not silently weaken data protection. These extensions are beyond this focused assessment.

References: [Geolocator setup/settings](https://pub.dev/packages/geolocator), [Android location foreground service](https://developer.android.com/develop/background-work/services/fgs/service-types#location), [Apple background location](https://developer.apple.com/documentation/corelocation/handling-location-updates-in-the-background).

## Tests and builds

```sh
dart format --output=none --set-exit-if-changed lib test mock_api
flutter analyze
flutter test --reporter expanded
flutter build apk --debug
# macOS only; signing is needed to install on a physical iPhone
flutter build ios --debug --no-codesign
```

Tests use actual temporary SQLite databases, injected location/network streams and mock HTTP clients. They cover offline persistence/restart, reconnection sync, duplicate protection, retries and saved deadlines, overlapping triggers, permanent rejections, transport timeouts, server commit followed by a failed reply, native settings, and a GetX lifecycle test showing that minimize does not cancel capture. Configuration/lifecycle tests do not prove all device background behavior: validate screen lock on a real Android/iPhone as well.

The optional [native Android emulator check](docs/android-emulator-check.md) verifies actual GPS callbacks while minimized/screen-off and reconnect synchronization. It is separate from the normal unit tests. On Windows, `kotlin.incremental=false` avoids Kotlin's cross-drive Pub-cache error; it changes build caching, not app behavior.

GitHub Actions runs analysis/tests and an Android APK build, plus an unsigned iOS build on macOS. The Android APK is attached as a CI artifact. Signing, store submission, authentication, encryption, batching and retention cleanup are outside this small demonstration.

### Verification performed

- All 14 device-independent tests passed; analysis reported no issues.
- The Android debug APK compiled successfully.
- The native integration test passed on the Android 17 emulator: actual GPS fixes arrived while minimized and screen-off, Stop removed the foreground service, and reconnection synchronized the pending records. No Flutter frames were pumped during the background wait.
- An unsigned iOS debug build passed on the macOS CI runner. iPhone screen-lock behavior has not been tested on a physical device.
